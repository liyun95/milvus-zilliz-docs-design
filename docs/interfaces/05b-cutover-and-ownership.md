# 05b 页面切换与归属

迁移期间，同一页可能在飞书和 Git 两边都有内容，Fetch 每次运行都要知道该用哪一边。本篇定义一页怎样从飞书交给 Git、怎样从 Git 下线，以及期间导航与归属怎样划分。生成结果怎样写入 dev 见 [05](./05-publish-handoff.md)。

**参与方**：文档负责人（激活）、zdoc 发布（Fetch 工作流）、飞书知识库目录与多维表格（首期仍决定导航）。

**状态**：已定义，待文档负责人确认；首期导航方案待确认（见[首期实施计划第 6.1 节](../phase-1.md#61-待确认的接口)）。

## 约定

### 导航（首期）

首期，迁移页的导航仍由飞书目录管理：

- 迁移页在飞书知识库目录中的节点和多维表格记录**保留**，只用来决定它在导航中的位置、顺序和标签；正文和其余元数据由 Git 生成。
- 导航生成遇到迁移页的节点时，不渲染飞书正文，改用 Git 的生成结果；front matter 中的 `sidebar_label`、`sidebar_position` 按飞书记录填写，与导航一致。
- 页面配置中不写导航标签和排序（见 [02](./02-page-config.md)）。调整迁移页在导航中的位置，和其他页面一样在飞书目录中操作。
- 飞书记录的发布目标与页面配置的 `publish` 必须一致，包括手册和路径（`publish[].path`）。
- 其他导航项对迁移页的引用依赖飞书记录，记录保留后照常有效。

范围内的页面大批迁移、停用飞书抓取时，再把导航整体迁到 Git。这一选择待文档负责人确认（见[首期实施计划第 6.1 节](../phase-1.md#61-待确认的接口)）。

### 归属与生效配置

| 规则 | 做法 |
|---|---|
| 生效配置 | `active.json` 列出已切换到 Git 的页面标识，以及切换它的那次运行。它在 dev 中，由 Fetch 写入，人不手改：激活时加入，下线完成时移除，都与这一页的输出在同一个 dev 提交中 |
| 飞书让路 | Fetch 渲染飞书时跳过清单中页面的正文；飞书记录被修改或删除，都不能改写或删除这些页面的输出与译文 |
| 不许重复 | 同一个输出路径既有飞书页面又有 Git 页面时，生成失败 |
| 切换前只生成候选 | `page.yaml` 合并到 master 后，Git 版本只作为候选生成、供预览，不写入 dev；飞书仍是正式来源 |

### 切换与激活

![一个页面从飞书切换到 Git 的三个状态：准备中，飞书仍是正式来源，Git 输入只生成预览；激活，一个受控 dev 提交同时写入生效配置、正文、导航和来源记录，旧飞书任务同时失去写权；已切换，正式来源是 Git，飞书任务不能写入或删除该页。准备中遇到失败、取消或基线变化时保持原状；已切换后部署失败时重试或回滚，来源仍是 Git。](../assets/page-cutover-states.png)

图 1 · 一个页面从飞书切换到 Git

- **激活由文档负责人手动触发，分两次运行。** 先触发一次带“比较某页”参数的 Fetch：生成 Git 版本，与飞书当前版本比较，差异写进运行结果，不写 dev。文档负责人看过差异，确认飞书最近的修改已反映到 Git 中（或这一页已在飞书暂时冻结）后，再触发一次带“激活某页”参数的 Fetch。
- **激活时工具检查能检查的。** 能生成；图片与链接都能解析；飞书节点存在，发布目标与路径一致。任何一项不满足就不激活。候选结果是否审核过、飞书修订是否核对过，由文档负责人在触发前确认，工具不判断。
- **激活是同一个提交。** 这次运行在同一个 dev 提交中写入 `active.json`、两个手册的 MDX、导航与记录文件；从这次提交起，飞书不再生成这一页。串行队列只保证顺序，不能代替这一同批提交。等待期间发布基线变化，候选需要重新生成和审核；重试应识别同一次发布，不恢复旧来源。
- **部署不是同一个事务。** 站点部署在激活之后进行，失败时走既有的重试或镜像回滚，编辑来源仍是 Git，不自动交回飞书。首期不提供切回飞书；激活后出了问题，用 dev 的恢复流程或镜像回滚处理（见 [05](./05-publish-handoff.md#恢复)）。
- **旧任务必须遵守归属。** 飞书全量抓取、旧缓存、删除清单和恢复任务都不能改变已迁移的页面；重复路由或 ID、错误来源的写入和删除直接失败；未迁移页面照常更新。Milvus 侧若仍有飞书导入任务，也要撤销它对已迁移共享原文的覆盖能力。
- **迁移不只是正文。** 附件、图片、同步块和必要元数据也要迁移；仍依赖飞书同步块的页面不算完全迁出。导航首期仍由飞书目录管理。

一页完成迁移的标准：从批准的 Git 输入生成并上线，旧任务不能改变结果，资源可以重建，翻译输入有效，编辑入口明确；导航位置首期仍在飞书目录中维护。范围内的页面和依赖迁完后，再停用相应的飞书抓取与调度。

### 下线完成

下线的页面经提升后，页面目录在 master 中被删除（见 [04](./04-channels-and-lock.md#下线一页)）。首期导航仍由飞书节点决定，这个节点由发起提升的文档工程师在提升 PR 合并后删除：删早了，Prod 还在显示这一页，导航里却没有它；不删，这一页离开 `active.json` 后会被飞书当作普通页面重新生成。Fetch 按节点是否已删除处理：

| 提升合并后，Fetch 看到页面目录已删除 | 做法 |
|---|---|
| 飞书节点已删除 | 在同一个 dev 提交中删除这一页两个手册的 MDX、译文与记录文件，并把它从 `active.json` 移除，网站上这一页消失 |
| 飞书节点还在 | 不改动 dev 中这一页的任何文件，网站维持原样，并通知发起提升的文档工程师删除飞书节点；删除后，下一次 Fetch 自动完成上一行 |

尚未激活的页面被删除时，只是不再生成候选结果，不涉及 dev。

## 出错时

| 情况 | 结果 |
|---|---|
| 同一个输出路径既有飞书页面又有 Git 页面 | 生成失败 |
| 飞书记录的发布目标或路径与页面配置的 `publish` 不一致 | 该页生成失败 |
| 飞书任务试图改写或删除已切换页面的输出 | 失败，已切换页面保持不变 |
| 激活时工具检查不通过（不能生成、图片或链接无法解析、飞书节点不存在或不一致） | 不执行激活，飞书仍是正式来源 |

## 例子

<details>
<summary>Delete Entities 的激活（示意）</summary>

1. 接入 PR 合并后，Fetch 每次运行都为 Delete Entities 生成候选结果，不写入 dev，网站上仍是飞书版本。
2. 文档负责人触发一次带“比较 `delete-entities`”参数的 Fetch，查看 Git 版本与飞书当前版本的差异，确认飞书最近的修改已反映到 Git 中。
3. 文档负责人触发一次带“激活 `delete-entities`”参数的 Fetch。工具检查通过后执行激活。
4. 这次运行在同一个 dev 提交中写入 `generated/en/manifests/shared-pages/active.json`：

```json
{
  "schema_version": 1,
  "pages": [
    { "page": "delete-entities", "activated_by": "<这次 Fetch 的运行编号>" }
  ]
}
```

以及 Guides 与 BYOC 两份 MDX、导航和 `delete-entities.json` 记录文件。从这次提交起，飞书不再生成这一页；它在导航中的位置仍由飞书节点决定。

</details>

## 设计理由

<details>
<summary>展开设计理由</summary>

**为什么首期导航仍由飞书管理。** Guides 的导航从飞书知识库目录树生成：工具逐层遍历节点，同一层按多维表格的 `Sidebar Order` 排序，标签也来自多维表格；页面 front matter 中的 `sidebar_position` 只是按这个顺序算出的结果。首期只迁 3 页，其余 360 多页的导航仍在飞书。另一种做法是删除迁移页的飞书节点，让 Git 页面按 `page.yaml` 的路径与排序插入导航：可以完全迁出，但要新增把 Git 页面插进飞书导航的合并规则，处理其他导航项对它的引用，作者调整导航时也要面对两套规则。

**为什么 `active.json` 放在 dev、由 Fetch 写入。** zdoc 约定 master 放工具，dev 放内容和发布状态，`active.json` 属于发布状态。“这一页由 Git 管”和“这一页的 Git 生成结果”必须在同一个提交中生效，否则会出现清单说归 Git、dev 中却还是飞书内容的情况。

**为什么激活与提升分开。** 激活决定这一页由谁生成（飞书或 Git），一页只做一次，由文档负责人把关；提升决定 Prod 用哪个版本，每次上线都做，由 文档工程师发起（见 [04](./04-channels-and-lock.md#lockyaml-怎样变化)）。两者互不依赖：功能未上线的新页面可以先激活、只在 UAT 显示，上线时再提升。

**为什么下线完成要看飞书节点。** 首期导航由飞书节点决定。节点删早了，Prod 还在显示的页面会从导航中消失；节点不删，这一页离开 `active.json` 后会被飞书重新生成。所以由 Fetch 在两个条件都满足时才移除。

**为什么激活前先比较一次。** 接入 PR 合并后，候选结果只在 Fetch 的临时产物中，没有地方可以看；接入之后，飞书上也可能又有人改过这一页。先比较一次，把 Git 版本与飞书当前版本的差异写出来，文档负责人才有东西可审。

**为什么首期不提供切回飞书。** 切回要把页面移出 `active.json`、让飞书重新生成，还要处理期间在 Git 中做的修改。首期只有 3 页，出了问题用 dev 的恢复流程或镜像回滚就能处理。

</details>
