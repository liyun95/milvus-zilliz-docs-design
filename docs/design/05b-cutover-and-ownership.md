# 05b 页面切换与归属

**这一篇只在 Phase 1 过渡期存在。** Phase 1 中飞书还不能退出：每一页原本都在飞书中编写，导航也仍由飞书目录决定。所以迁移期间，同一页可能在飞书和 Git 两边都有内容，Fetch 每次运行都要知道该用哪一边。本篇定义这个开关（飞书表格的 placement type，以及 Fetch 按它生成的 `active.json`）、一页怎样从飞书交给 Git（激活）、交给 Git 之后飞书怎样让路，以及怎样下线。飞书退出后，本篇的大部分内容不再需要。生命周期的总览见[接口设计 README](../prd.md#4-一页的生命周期)；生成结果怎样写入 dev 见 [05](./05-publish-handoff.md)。

对应的产品需求见[产品需求场景 9](../prd.md#场景-9从飞书切换到-git激活)、[场景 10](../prd.md#场景-10下线一页)。

**参与方**：文档负责人（比较与激活）、文档工程师（下线）、zdoc 发布（Fetch 工作流）、飞书知识库目录与多维表格（Phase 1 仍决定导航、来源与整页通道）。

**状态**：由原接口设计迁入，2026-10-20 按文档负责人的意见改为在飞书表格中激活与下线，待工程维护者完善。

## 约定

### 开关（placement type）

一页由飞书还是 Git 生成，由飞书表格中这一页记录的 placement type 决定。zdoc 现有 `canonical`、`section`、`link`、`ref` 四个值（`packages/docs-tooling/src/lark/guidesBaseRecordSemantics.js`），其中 `canonical` 表示由飞书文档生成的页面。Phase 1 新增 `git`，表示由 Git 生成：

- 标为 `git` 的记录不填 `Docs`（飞书文档链接）。发布目标（`Targets`）、路径、`Progress`、`Release Channel` 与导航用的标签和排序照常填写，发布目标与路径必须与页面配置的 `publish` 一致。
- Fetch 读到 `git` 记录时，不抓飞书正文，改用 `shared-docs/pages/<页面标识>/` 的生成结果；导航仍按这条记录生成。

### 生效配置（`active.json`）

**`active.json` 是 Fetch 按表格生成的派生记录**，列出已经交给 Git 的页面。它放在 dev 中的 `generated/en/manifests/shared-pages/active.json`，与各页的记录文件同一目录（见 [05](./05-publish-handoff.md#记录文件)），人不手改。

```json
{
  "schema_version": 1,
  "pages": [
    { "page": "delete-entities", "record": "recXXXXXXXX", "activated_in": "11873360452" },
    { "page": "filtered-search", "record": "recYYYYYYYY", "activated_in": "11902245810" }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `schema_version` | 格式版本，目前为 `1` |
| `pages[].page` | 已交给 Git 的页面标识 |
| `pages[].record` | 飞书表格中对应记录的 ID |
| `pages[].activated_in` | 第一次按 Git 生成这一页的 Fetch 运行编号（GitHub Actions 的运行 ID），用于追溯 |

- **只在两个时刻变化**：激活后的第一次 Fetch 加入一项，下线完成的那次 Fetch 删除一项（见下文）。其余运行照抄。
- **与页面内容同一个提交**：加入或移除时，这一页的 MDX、导航与记录文件在同一个 dev 提交中写入或删除，不会出现清单说归 Git、dev 中却还是飞书内容的情况。
- **它有三个用处**：Git 中有一份可以追溯的记录；dev 上的检查不调用飞书，就能拦住改写已激活页面的提交；Fetch 每次把表格与上一次的清单对比，发现 placement type 被改回其他值时失败（见下文“出错时”）。
- 飞书退出时，`active.json` 可以直接改为正式来源，不再从表格生成。

### 切换与激活

激活就是把一页的 placement type 改为 `git`，一页只做一次，由文档负责人进行。Fetch 要新增一种可以手动发起的运行：只比较某一页。做成 Fetch 的参数还是单独的工作流，由 zdoc 维护者确定。激活本身不是一次运行，是表格中的一次修改。

![一个页面从飞书切换到 Git 的三个状态：准备中，飞书仍是正式来源，Git 输入只生成预览；激活，一个受控 dev 提交同时写入生效配置、正文、导航和来源记录，旧飞书任务同时失去写权；已切换，正式来源是 Git，飞书任务不能写入或删除该页。准备中遇到失败、取消或基线变化时保持原状；已切换后部署失败时重试或回滚，来源仍是 Git。](../assets/page-cutover-states.png)

图 1 · 一个页面从飞书切换到 Git

这张图从实现角度画切换前后的状态，没有画激活前的比较与确认；从文档负责人角度看的三步见[产品需求场景 9 图 2](../prd.md#场景-9从飞书切换到-git激活)。

1. **比较。** 文档负责人手动发起一次“比较”运行，指定这一页。运行把两份 MDX 逐个手册比较：一份是按 `lock.yaml` 与 `page.yaml` 生成的 Git 版本（两个版本已合并），一份是同一次运行从飞书渲染出的这一页，也就是网站当前的内容。同时做激活前的检查：能生成；图片与链接都能解析；飞书表格记录的发布目标与路径与页面配置一致。差异与检查结果写进这次运行的结果（如运行摘要或可下载的产物），不写 dev。
2. **确认。** 文档负责人看过差异，确认飞书最近的修改已反映到 Git 中（或这一页已在飞书暂时冻结），并确认候选结果已审核。这两项由人判断，工具不检查。
3. **激活。** 文档负责人在飞书表格中把 placement type 改为 `git`。
4. **下一次 Fetch 同一个提交写入。** Fetch 读到 `git` 记录，再做一遍第 1 步的检查。通过后，在同一个 dev 提交中写入 `active.json`、两个手册的 MDX、导航与记录文件；从这次提交起，飞书不再生成这一页。不通过时，这一页保留 dev 中现有的版本（第一次激活时就是飞书版），不退回飞书重新生成，并发飞书卡片通知文档负责人。
5. **部署。** 站点部署在激活之后进行，不与激活在同一个事务中；失败时走既有的重试或镜像回滚，编辑来源仍是 Git，不自动交回飞书。

全新的页面没有飞书版：在表格中新建记录时直接标为 `git`，不需要比较；第一次 Fetch 同样按第 4 步写入。

### 激活之后的归属规则

以下规则在 Phase 1 中新增：现有的 Fetch 和相关任务没有“页面归属”的概念，所有页面都从飞书生成。每次运行都先读飞书表格与 `active.json`，按它们决定每一页听谁的；具体在哪些任务中怎样实现，由 zdoc 维护者确定（见 [Phase 1 实施计划第 6.1 节](../phase-1.md#61-待确认的接口)中的“Fetch 的接入点”）。

| 规则 | 做法 |
|---|---|
| 飞书让路 | Fetch 渲染飞书时跳过标为 `git` 的记录的正文；飞书文档被修改或删除，都不能改写或删除这些页面的输出与译文 |
| 不许重复 | 同一个输出路径既有飞书页面又有 Git 页面时，生成失败 |
| 旧任务遵守归属 | 飞书全量抓取、旧缓存、删除清单和恢复任务都不能改变已迁移的页面；重复路由或 ID、错误来源的写入和删除直接失败；未迁移页面照常更新。Milvus 侧若仍有飞书导入任务，也要撤销它对已迁移共享原文的覆盖能力 |
| 不切回飞书 | Phase 1 不提供切回飞书；激活后出了问题，用 dev 的恢复流程或镜像回滚处理（见 [05](./05-publish-handoff.md#恢复)） |

### 导航（Phase 1）

Phase 1，迁移页的导航仍由飞书目录管理：

- 迁移页在飞书知识库目录中的节点和多维表格记录**保留**，只用来决定它在导航中的位置、顺序和标签；正文和其余元数据由 Git 生成。
- 导航生成遇到迁移页的节点时，不渲染飞书正文，改用 Git 的生成结果；front matter 中的 `sidebar_label`、`sidebar_position` 按飞书记录填写，与导航一致。
- 页面配置中不写导航标签和排序（见 [02](./02-page-config.md)）。调整迁移页在导航中的位置，和其他页面一样在飞书目录中操作。
- 飞书记录的发布目标与页面配置的 `publish` 必须一致，包括手册和路径（`publish[].path`）。
- 其他导航项对迁移页的引用依赖飞书记录，记录保留后照常有效。

范围内的页面大批迁移、停用飞书抓取时，再把导航整体迁到 Git。这一选择已与文档负责人确认。

### 下线完成

Phase 1 下线沿用飞书表格现有的做法，与其他页面相同（zdoc `README.md` 中的 Release Channel gating 一节）：

| 步骤 | 谁 | 做什么 | 网站 |
|---|---|---|---|
| 决定下线 | 文档工程师 | 表格中把 `Release Channel` 改为 `RETIRE-IN-NEXT` | UAT 不再显示，Prod 照常；Fetch 照常生成，整页带 `channel: retire-in-next` |
| 发版 | 文档工程师 | 删除表格记录与飞书节点 | 下一次 Fetch 在同一个 dev 提交中删除这一页两个手册的 MDX、译文与记录文件，并把它从 `active.json` 移除 |
| 之后 | 文档工程师 | 普通 PR 删除 `shared-docs/pages/<页面标识>/`（见 [04](./04-channels-and-lock.md#删除页面目录)） | 无 |

- 表格中为 `RETIRE-IN-NEXT` 或已没有记录的页面，上游更新不再检查（见 [06](./06-upstream-changes.md#发现与运行)）。
- 记录已删除、目录还在：Fetch 不生成这一页，在运行摘要中提示删除目录。
- 目录已删除、记录还在且标为 `git`：这一页生成失败，保留 dev 中现有的版本并通知。

尚未激活的页面被删除时，只是不再生成候选结果，不涉及 dev。

### 一页完成迁移的标准

- 从批准的 Git 输入生成并上线，旧任务不能改变结果。
- 资源可以重建，翻译输入有效，编辑入口明确。
- 迁移不只是正文：附件、图片、同步块（飞书中多页共用的内容块）和必要元数据也要迁移；仍依赖飞书同步块的页面不算完全迁出。
- 导航位置 Phase 1 仍在飞书目录中维护。

范围内的页面和依赖迁完后，再停用相应的飞书抓取与调度。

## 出错时

| 情况 | 结果 |
|---|---|
| 同一个输出路径既有飞书页面又有 Git 页面 | 生成失败 |
| 飞书记录的发布目标或路径与页面配置的 `publish` 不一致 | 该页生成失败 |
| 飞书任务试图改写或删除已切换页面的输出 | 失败，已切换页面保持不变 |
| 比较时检查不通过（不能生成、图片或链接无法解析、表格记录不一致） | 运行结果中列出，不应激活 |
| 标为 `git` 后 Fetch 检查不通过 | 这一页保留 dev 中现有的版本，通知文档负责人 |
| 表格标为 `git`，但没有对应的页面目录 | 这一页生成失败，保留 dev 中现有的版本 |
| `active.json` 中的页面，表格中的 placement type 被改回其他值 | Fetch 失败，页面保持 Git 版；要切回飞书不在 Phase 1 范围内 |

## 设计理由

<details>
<summary>展开设计理由</summary>

激活与提升分开、在飞书表格中激活与下线、不提供切回飞书的理由见[产品需求场景 9](../prd.md#场景-9从飞书切换到-git激活)、[场景 10](../prd.md#场景-10下线一页)。

**为什么 Phase 1 导航仍由飞书管理。** Guides 的导航从飞书知识库目录树生成：工具逐层遍历节点，同一层按多维表格的 `Sidebar Order` 排序，标签也来自多维表格；页面 front matter 中的 `sidebar_position` 只是按这个顺序算出的结果。Phase 1 只迁 3 页，其余 360 多页的导航仍在飞书。另一种做法是删除迁移页的飞书节点，让 Git 页面按 `page.yaml` 的路径与排序插入导航：可以完全迁出，但要新增把 Git 页面插进飞书导航的合并规则，处理其他导航项对它的引用，作者调整导航时也要面对两套规则。

**为什么以表格为来源、`active.json` 只是派生记录。** 人只在一处操作，两处不会不一致；表格是文档负责人维护导航的地方，激活与其他页面的维护方式相同，不用另建激活工作流与 GitHub 环境审批。代价是表格的修改没有 PR 审核，所以用 Fetch 的检查和 `active.json` 的对比兜底。

**为什么 `active.json` 放在 dev、由 Fetch 写入。** zdoc 约定 master 放工具，dev 放内容和发布状态，`active.json` 属于发布状态。“这一页由 Git 管”和“这一页的 Git 生成结果”必须在同一个提交中生效，否则会出现清单说归 Git、dev 中却还是飞书内容的情况。

**为什么激活前先比较一次。** 接入 PR 合并后，候选结果只在 Fetch 的临时产物中，没有地方可以看；接入之后，飞书上也可能又有人改过这一页。先比较一次，把 Git 版本与飞书当前版本的差异写出来，文档负责人才有东西可审。

</details>
