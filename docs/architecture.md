# 共享文档架构设计

本文面向 zdoc 与 md2md 的维护者，说明系统怎样搭建、边界在哪里，供实现设计会使用。为什么改、改完后怎样协作，见[方案总览](./proposal.md)；实施顺序与验收见[首期方案](./phase-1.md)。

文中标为“待定”的内容与方案总览第 6 节的待确认事项一致，会后按结论更新。生产实现与集成验收尚未完成。术语见[第 8 节](#8-术语)。

## 1. 架构一览

![目标工具链：Milvus 侧沿用 milvus-docs → md2md → web-content → milvus.io；zdoc 从 milvus-docs 直接读取固定版本原文，结合页面配置、变量和 Cloud 内容文件生成 Cloud 页面，经升级 PR 采用后进入 zdoc 既有发布流程。](./assets/target-publication-chains.png)

图 1 · 目标工具链（与方案总览图 3 相同）
三条设计原则：

- **一个编辑源。** 共享原文只在 milvus-docs 维护；Cloud 从 md2md 处理前的固定 commit 读取，不从 web-content 或站点 HTML 反推。
- **差异放在 zdoc。** Cloud 的章节与段落差异写在 zdoc 的 overlay（页面配置、变量、Cloud 内容文件）中，原文只提供中性的命名块，代码行级的差异也写在 zdoc（[第 2.3 节](#23-代码行差异)）。
- **新增只在前端。** 新增工作是 zdoc 的共享获取与生成，以及 md2md 的预处理入口；校验、过滤、翻译与发布沿用 zdoc 现有流程，只扩展 Git 输入。不新增在线 registry、内容包分发服务或另一条发布队列。

| 仓库 | 负责什么 | 首期改动 |
|---|---|---|
| [milvus-docs](https://github.com/milvus-io/milvus-docs) | 共享原文、命名块、默认变量 | 加变量与命名块；更新贡献说明 |
| [md2md](https://github.com/zilliztech/md2md) | 变量与片段 include 的展开 | 新增只做预处理的入口；新增命名块标记清理，供 Milvus 发布使用 |
| [zdoc](https://github.com/zilliztech/zdoc) | Cloud overlay、页面生成、升级 PR、发布 | 新增共享获取与生成；扩展来源、通道与发布接入 |
| [web-content](https://github.com/milvus-io/web-content) → [milvus.io](https://github.com/milvus-io/milvus.io) | Milvus 发布；SDK Reference 原文 | 不变，只做回归验证 |

**共享原文的把关。** milvus-docs 的 PR 按 Milvus 既有流程审核，Cloud 侧不设 CODEOWNERS。只适用于 Milvus 的内容进入共享原文后，Cloud 在升级 PR 中处理：暂缓采用、请求改为两端通用的写法，或在 zdoc 中移除。

本设计仓库只保存方案与验证样例，不参与生产发布；样例中的仓库目录是输入示意，不是第三份内容来源。

## 2. 页面生成

![Cloud 页面生成流水线：①按 lock 中 current / next 两个 commit 获取 milvus-docs 原文；②定位命名块与代码组并生成 registry；③按页面配置对命名块、语言示例或连续的代码行执行 add、replace、remove；④调用 md2md 预处理入口展开变量与片段；⑤沿用 zdoc 现有的产品过滤，只处理 Cloud 内容中的指令；⑥站点适配。两个版本各走一遍，按块比较后把不同的块成对包进 NextChannel，输出一份 MDX。下方对照 Milvus 侧：md2md 用 Milvus 变量展开并清除命名块标记。](./assets/generation-pipeline.png)

图 2 · Cloud 页面生成流水线
- **顺序是约束，不是实现细节。** 命名块必须在变量展开之前定位，因为标记只存在于原文中；Cloud 内容文件在第 3 步插入后，与原文一起在第 4 步展开变量。本地原型也按这个顺序实现。
- **md2md 只提供预处理。** zdoc 调用 md2md 新增的预处理入口，不运行会执行 Milvus 站点插件的完整转换入口。zdoc 现有的 LarkDocWriter 接收飞书 JSON，不能充当 Markdown 编译器；现有 local source 也没有 Git 锁定与命名块消费。[复用审计](../research/md2md-zdoc-reuse-audit.md)
- **站点适配不承担业务差异。** 第 6 步只负责 Tabs、提示组件、链接、图片和元数据，不为某种业务差异增加专门的处理。

### 2.1 命名块与注册

```markdown
<!-- doc:block:start id="standard-filtering-code" -->
完整的共享代码组，或需要被替换的一节。
<!-- doc:block:end id="standard-filtering-code" -->
```

- **只在需要差异处理的位置命名。** 无差异的页面整篇复用，不需要任何命名块。标记是中性的，不表达 Cloud 的产品选择。
- **注册只登记文件，块由工具扫描。** 人工登记源文件和稳定的模块 ID，工具扫描其中的命名块，生成 registry（文件、块、类型、语言、摘要和来源）。新增命名块不需要再手工登记。注册文件的位置与是否单独保留，待与 zdoc 维护者确定（[消费配置草案](./consumption-schema.md)）。
- **按身份定位，不按行号。** 模块 ID 在 registry 内唯一，块 ID 在模块内唯一；文件改名时只改映射，ID 不变。行号只用于报错。
- **结构错误直接失败。** 重复 ID、未闭合或交叉的边界、空块、非法嵌套都报错；识别标记时区分 Markdown 与代码上下文，不把示例字符串误认为标记。只支持 Markdown 块和完整代码组，不支持代码内部的子区域。
- **registry 可重建。** registry 和提取结果是 zdoc 内部的生成物，每次在干净目录中生成，不作为编辑源。

### 2.2 差异与变量

页面配置只做三种动作：`add`、`replace`、`remove`。目标可以是一个命名块、代码组中的一个语言示例，或语言示例中连续的几行（第 2.3 节）。Current / Next 不在这里声明，由 lock 中的两个版本自动区分（第 4 节）。动作写法和冲突规则见[消费配置草案](./consumption-schema.md)。

变量沿用 md2md 的 `Variables.json` 与 `{{var.xxx}}`：

- Milvus 默认值在 `site/en/Variables.json`，Cloud 在显式的消费根目录读取同名文件。同一产品的各 SDK 共用连接变量。
- 产品展示名称用 `product_name`；`MilvusClient`、包名、命令以及明确讨论 Milvus 本身的文字保留真实名称。产品功能或流程不同，不能靠改名掩盖。
- 变量只放小粒度的值，不放整行代码。缺少 Cloud 绑定时失败，不静默使用 Milvus 的值。
- 接入时核实 md2md 原有的目录与页面作用域，保持旧入口兼容；新约定使用显式根目录，首期不引入多层隐式继承。

### 2.3 代码行差异

同一段代码中只有个别行因产品而不同时，例如 embedding 函数参数中 Milvus 的可选 `credential` 注释与 Cloud 必填的 `integration_id`，原文的代码不改，只给代码组加命名块；zdoc 在页面配置中按原文里连续的整行定位并修改。示意见方案总览图 5。

```yaml
- operation: replace
  target:
    module: openai
    block: define-function-code
    language: python
    lines: |
      # Optional parameters:
      # "credential": "apikey_dev",
  content:
    lines: |
      "integration_id": "YOUR_INTEGRATION_ID",
```

- **定位规则。** 只在已经定位的代码组和语言示例内查找；`lines` 是一行或连续的几行，比较时忽略行首缩进和行尾空格，其余必须完全一致，并且恰好出现一次。最多 5 行。
- **三种动作照旧。** `replace` 换掉这几行，`remove` 删掉，`add` 配合 `position: before | after` 在这几行前后插入。
- **缩进。** 新内容以被定位的第一行的缩进为基准，保留各行之间的相对缩进。
- **失败关闭。** 匹配不到、出现多次、超过上限或目标语言不存在，都直接失败。上游改了被定位的行时，引用它的页面不能升级，旧版本继续有效。
- **超出范围就替换整个语言示例。** 一段代码中有多处不同，或连续超过 5 行，改为替换该语言示例（`language` 级）。

原文中不写任何产品指令，Milvus 侧也不需要新增产品过滤；md2md 只清除命名块标记。不采用以下做法：

- **在原文中写 zdoc 产品行指令**（`include-next-line zilliz|milvus`）：Cloud 的代码会进入 Milvus 原文，Milvus 作者修改代码时要同时照顾 Cloud 的行，Milvus 发布链还要新增一套与 zdoc 理解一致的过滤。
- **在代码中加区域标记再替换**：标记要按每种语言写成注释，在代码内部清理，替换时还要按标记位置处理缩进。

### 2.4 页面类型

- **整篇复用**：只有产品名、endpoint、token 或元数据不同。一份页面配置，无命名块。
- **整篇复用并加差异**：只在需要处理的位置命名，差异在同一份页面配置中声明。
- **独立编排并引用共享命名块**：产品确实需要不同的章节结构时使用，保留为扩展路径，首期不实现。
- **Cloud 独有页**：不引用共享原文，在 zdoc 维护完整原文，首期不迁移。

标题相同时随正文引用。先消除可以合并的历史漂移，再编码必须保留的产品差异；缺少语言、旧 SDK 写法或错误示例不能当作长期差异。

## 3. 上游变化与升级 PR

![上游变化成为 Cloud 升级 PR 的过程：milvus-docs 的 PR 经 CI 检查后合并；zdoc 工具发现新提交，固定 commit 重新生成并比较变化，在 zdoc 发起附 lock、生成差异和影响报告的升级 PR；命名块被删除或改名时阻止升级，旧版本继续有效。Cloud 文档工程师审核：修改则回到源文件，暂缓则保持旧版本，合并则更新 lock 的 next，新版本先在 UAT 可见；Cloud 发布时把 current 改为 next，Prod 采用新版本。](./assets/upgrade-pr-flow.png)

图 3 · 上游变化怎样成为 Cloud 的升级 PR
- **升级就是一个普通的 zdoc PR。** PR 中更新 lock 的 `next`，附生成结果的差异、预览和影响报告；审核与批准沿用 GitHub PR，不另建审批记录。lock 和依赖索引由工具生成，写作者不手填 hash。
- **Cloud 发布时提升。** 把 lock 的 `current` 改为 `next` 的值，Prod 采用 UAT 已经在显示的版本。提升也是一个普通 PR，可由工具一次覆盖所有页面。
- **跟踪分支只用于发现变化。** 正式生成始终使用 lock 中固定的 commit。
- **待定：** lock 的粒度（每页独立采用还是全仓统一）、Cloud 跟踪哪个 Milvus 版本分支、发现方式（定时或事件触发）及其执行身份、提升由谁在发布流程的哪一步发起。

不同的上游变化，工具应有的行为：

| 上游变化 | 行为 |
|---|---|
| 新增合法的命名块 | 自动进入 registry，不自动升级或发布 |
| 移动块或修改标题，ID 不变 | 身份保持，检查内容和上下文变化 |
| 块改名或删除 | 引用它的页面不能升级，旧版本继续有效，需要显式迁移 |
| 被 Cloud 替换的原文发生变化 | 即使 Cloud 输出不变，也提示复核 |
| 被 Cloud 按行定位的代码行被修改 | 匹配失败，引用它的页面不能升级，旧版本继续有效 |
| Cloud 规则只在 `next` 上失效 | 升级 PR 失败并指出通道，`current` 与 Prod 不受影响 |
| 类型、上下文或语言变化 | 检查兼容性，不静默组装 |
| 只新增标记，正文未变 | 更新身份与依赖，不触发重译 |

影响报告按页汇总：代码组报告完整代码组的上下文，Markdown 块报告页面上下文，按行定位的规则随所在代码组报告。摘要只能发现变化，不能判断语义是否一致，首期提示可以保守。

## 4. 发布通道与内容过滤

zdoc 已有两套互不干扰的过滤，共享内容直接复用：

- **产品过滤**（zilliz、saas、paas、milvus 等目标）在 Fetch 阶段执行。共享原文不写产品指令；Cloud 内容文件迁入 Git 后仍可使用现有指令，处理对象从飞书输入扩展到 Git 输入。
- **发布通道**（Current / Next）在渲染阶段执行：UAT 与 Prod 使用同一镜像，部署时注入通道，按通道显示内容。

| 需要只在 Next 显示的内容 | 写在哪里 |
|---|---|
| Cloud 内容文件中新增或替换的内容 | 在文件里直接使用 `<NextChannel>` |
| 整个 Cloud 页面 | 页面配置中的通道字段（待定） |
| 共享原文中的变化 | 不需要写。lock 记录 `current` 与 `next` 两个版本，工具自动区分 |

共享原文不写通道标记，也不为通道加命名块。场景说明见[方案总览第 4.1 节](./proposal.md#41-milvus-先上线cloud-后上线的内容)。

**共享原文按两个版本生成。**

- lock 记录两个 milvus-docs commit：Prod 读 `current`，UAT 读 `next`。升级 PR 只改 `next`；Cloud 发布时把 `current` 改为 `next`（提升）。
- 两个版本各自走完第 2 节的生成流程。Cloud 规则在两边都必须成立，失败时指出是哪个通道。
- 结果按顶层块比较：标题、段落、整个列表、表格、提示框各算一块，代码组整体算一块。相同的块只输出一次；连续的不同块输出成 `exclude`（旧）与 `include`（新）一对；只在一侧存在的块只输出那一侧。
- 两个版本相同时，输出不带通道标记，与单版本生成的结果逐字相同。提升之后即是这种状态。
- front matter 无法按通道区分，两版不同时沿用 `current`，并记录在 receipt 中。
- 标题变化会让两个通道的目录与锚点不同，生成时给出提示。
- Cloud 内容文件中手写的 `<NextChannel>` 若落在成对的区域内，生成失败，避免嵌套。
- 例外：一部分修改需要提前进入 Prod 时，把 `current` 一并更新，再用命名块把尚未上线的一段包进 `<NextChannel>`。

规则与测试见[本地原型](../examples/filtered-search/two-commit/walkthrough.md)。仍需在 zdoc 中核实：`<NextChannel>` 包住列表、提示框和代码 Tabs 时的渲染，以及目录是否过滤其中的标题。

**一项飞书依赖。** 整页通道目前记录在飞书多维表格的 `Release Channel` 字段中（新记录默认 `NEXT`），并通过飞书文档 token 传递到译文。Git 来源的页面需要等价的通道字段与页面身份，例如写在页面配置中；接入时与翻译流程一并验证。[核验记录](../research/zdoc-variants-and-channels-audit.md)

## 5. 发布接入与保护

生成结果接入 zdoc 现有的内容暂存区（stage）、校验和串行发布队列。Git 页面和未迁移的飞书页面可以同批发布，但同一页不能有两个来源。

**生成文件不作为编辑源。** 保护靠受控来源、重新生成比对和分支权限共同实现：

| 环节 | 要求 | 首期 |
|---|---|---|
| 源 PR | 作者只改 Milvus 原文或 zdoc overlay；预览提供跳转到源文件的编辑入口 | 实现 |
| 分支权限 | 普通作者不能直接推送、强推正式生成分支，也不能绕过检查 | 实现 |
| 候选任务 | 可以生成和预览，没有生产分支或部署写权限；社区 PR 不需要 Cloud 凭据 | 实现 |
| 采用批准 | 以 zdoc 升级 PR 的审核合并为准；配置中自称已批准不构成授权 | 实现，沿用 GitHub PR |
| 重新生成比对 | CI 按 lock 中的固定输入在干净目录重新生成，与提交的结果不一致即失败，并指出应改的源文件 | 实现 |
| 产物绑定 | 校验结果绑定实际发布产物的摘要，校验后替换产物时部署拒绝 | 后续按实际风险评估 |
| 核心保护 | 工作流和校验器的改动需工程审核，内容 PR 不能关闭保护 | 实现 |

lock 与 receipt 用于追溯，不是签名或授权。批准后输入发生变化，需要重新检查和审核。

## 6. 按页迁移与正式激活

![一个页面从飞书切换到 Git 的三个状态：准备中，飞书仍是正式来源，Git 输入只生成预览；激活，一个受控 dev 提交同时写入生效配置、正文、导航和来源记录，旧飞书任务同时失去写权；已切换，正式来源是 Git，飞书任务不能写入或删除该页。准备中遇到失败、取消或基线变化时保持原状；已切换后部署失败时重试或回滚，来源仍是 Git。](./assets/page-cutover-states.png)

图 4 · 一个页面从飞书切换到 Git
- **同步配置只准备候选。** 新配置到达 dev 后只参与候选生成，当前生效的来源不变。
- **激活必须是同一个提交。** 生效配置、正文、必要导航、来源记录和 receipt 在一个受控的 dev 提交中写入，同时撤销旧来源的写权。串行队列只保证顺序，不能代替这一同批提交。等待期间发布基线变化，候选需要重新生成和审核；重试应识别同一次发布，不恢复旧来源。
- **部署不是同一个事务。** 站点部署在激活之后进行，失败时走既有的重试或镜像回滚，编辑来源仍是 Git，不自动交回飞书。重新交回飞书必须作为一次显式的来源切换来审核。
- **旧任务必须遵守归属。** 飞书全量抓取、旧缓存、删除清单和恢复任务都不能改变已迁移的页面；重复路由或 ID、错误来源的写入和删除直接失败；未迁移页面照常更新。Milvus 侧若仍有飞书导入任务，也要撤销它对已迁移共享原文的覆盖能力。
- **迁移不只是正文。** 切换前短暂冻结该页或核对最新的飞书修订；导航、附件、图片、同步块和必要元数据也要迁移。仍依赖飞书同步块的页面不算完全迁出。

一页完成迁移的标准：从批准的 Git 输入生成并上线，旧任务不能改变结果，资源可以重建，翻译输入有效，编辑入口明确。范围内的页面和依赖迁完后，再停用相应的飞书抓取与调度。

## 7. 翻译、恢复与运行

**翻译。** 翻译输入是完成组装、产品绑定和格式校验后的 Cloud 正文，沿用 zdoc 现有的 sourceHash、候选选择、语义单元、技术内容保护和批次机制，写作者不需要为翻译额外命名。Cloud 输出不变且已有有效译文时，不因被替换的上游内容变化而重译。英文站包含日文；中文是独立站点，公共构建改动按既有测试矩阵检查两站。

**恢复。** 先复用已有的 Git、媒体存储和发布记录，只补真实缺口，不先建完整归档：

| 恢复目标 | 复用什么 | 需要补的验证 |
|---|---|---|
| 生成正文、导航与译文状态 | zdoc 的 Git 修订和既有恢复流程 | 生效配置、来源记录与 receipt 纳入一致性检查 |
| 从共享源重建 | lock 中固定的 Milvus 与 zdoc 输入、工具和资源 | 输入仍可获取，重建结果与摘要一致 |
| 已发布站点回滚 | 既有成功发布记录和镜像 digest | 运维侧的保留策略与回滚接线可用 |

Git 中的图片按同一源修订读取；实际使用的外部图片需要固定字节摘要和可恢复的对象版本，不能只固定可被覆盖的 URL。源或资源缺失时直接失败，不回退到最新版本。镜像与图片的实际保留策略仍需运维核实。[恢复核验](../research/recovery-capability-audit.md)

**运行。** 同一 repository + commit 共用一次检出，每个注册文件只解析一次，只展开实际用到的部分。缓存身份包含全部输入：共享源、规则、变量、md2md 片段、Cloud 内容文件、资源、展示规则、工具及生效来源；冷热构建结果一致，飞书侧的“内容未变”不能跳过 Git 输入的变化。展开深度、体积、下载并发和超时都设上限，沿用原发布队列。

## 8. 术语

- **overlay**：zdoc 中只记录 Cloud 差异的一层文件，包括页面配置、Variables.json 和 Cloud 内容文件。是本次新建的，与 zdoc 现有的 `sidebar-overrides` 或部署仓库的 Kubernetes overlays 无关。
- **片段（fragment）**：milvus-docs 中多篇文章共用的一段内容，放在 `site/en/fragments/`，正文用 `{{fragments/xxx.md}}` 引用，由 md2md 展开。本方案只在这个意义上使用“片段”。
- **Cloud 内容文件**：一个共享页面中 Cloud 用来新增或替换的内容，与页面配置放在 zdoc 的同一目录（`shared-pages/<页面>/`），由页面配置的 `content.file` 指定。
- **命名块（block ID）**：原文中用 `doc:block` 注释标出的一段 Markdown 或一个完整代码组，是 Cloud 做差异处理的定位点。
- **registry**：工具扫描已登记文件后生成的命名块清单，包括类型、语言、摘要和来源。
- **lock**：一个页面当前采用的固定输入，包括 milvus-docs 的 `current` 与 `next` 两个 commit 和各输入的摘要。升级 PR 修改 `next`，提升修改 `current`。
- **提升（promotion）**：Cloud 发布时把 lock 的 `current` 改为 `next` 的值，Prod 采用 UAT 已在显示的版本。沿用 zdoc 对上线的叫法；共享页不需要逐处去掉标记。
- **receipt**：一次构建实际用到的输入、lock 和输出摘要，用于追溯和恢复一致性检查。
- **manifest**：来源版本、文件及摘要的清单，不能代替实际内容。
- **artifact**：构建产出的实际文件或包。
- **stage**：zdoc 现有发布流程中的内容暂存区，生成结果在这里校验后进入发布。
- **生效配置**：当前决定某页从哪个来源生成的配置。同步到 dev 的新配置在激活之前只用于候选。
