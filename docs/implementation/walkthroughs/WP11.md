# WP11 走读：两版合并

**仓库**：zdoc　**上游 PR**：[zilliztech/zdoc#921](https://github.com/zilliztech/zdoc/pull/921)，2026-10-29 合并（[`8404678a8`](https://github.com/zilliztech/zdoc/commit/8404678a8ec6dc91c890b367b6c243426bd4cd80)）；计划与审阅在 [liyun95/zdoc#14](https://github.com/liyun95/zdoc/pull/14)　**任务卡**：[WP11](../tasks/WP11-zdoc-two-version-merge.md)

## 解决什么问题

每一页的 `lock.yaml` 记着两个 milvus-docs commit：`current` 给 Prod，`next` 给 UAT（[技术设计 04](../../design/04-channels-and-lock.md)）。接入时两者相同；Milvus 原文有了 Cloud 还没上线的内容时，`next` 先往前走，两版就不同了。WP11 之前，工具遇到这种情况直接失败（“two-version merging requires WP11”）。

WP11 让这一页能生成：两版各生成一遍，再按块合成一份 MDX，相同的块只出现一次，不同的块用 `<NextChannel>` 成对输出（[产品需求场景 6](../../prd.md#场景-6让内容先只在-uat-显示)）。zdoc 网站已经认得这个组件：Prod 只显示 `exclude` 中的内容，UAT 只显示 `include` 中的内容。

```mdx
<NextChannel action="exclude">

旧的段落，只在 Prod 显示

</NextChannel>

<NextChannel action="include">

新的段落，只在 UAT 显示

</NextChannel>
```

**两版相同时，输出与以前逐字节相同。** 现在所有已接入的页面都是这种情况，生产上还没有一页的 `current` 与 `next` 不同：让 `next` 前进的是 WP12 的上游更新 PR。

## 一页经过的地方

合并放在站点适配之后、MDX 编译之前：

| 步骤 | 做什么 |
|---|---|
| 1. 两遍生成 | `current`、`next` 各自读取、变换、预处理、链接、站点适配（WP11 起每个通道只预处理一次，再按手册做产品过滤） |
| 2. 两版相同 | 站点适配后的内容逐字节相同时，直接走原来的路径，不切块、不合并 |
| 3. 切块 | 用 Markdown 解析器把两版各切成顶层块：标题、段落、整个列表、表格、提示框、整个代码组、HTML 块 |
| 4. 对齐 | 最长公共子序列：相同的块对上，中间不同的一串块作为一处改动 |
| 5. 输出 | 相同的块输出一次；改动处先 `exclude` 包住 `current` 的块，再 `include` 包住 `next` 的块；只在一边有的块只输出那一边 |
| 6. 一次定稿 | 合并后的页面只做一次 MDX 编译与产品名检查，`import` 按用到的组件生成 |

两版的 front matter 不同时，一律用 `current` 的值，并在结果的 `notes` 中记一条备注，`shared-docs build` 的输出摘要中显示。写进 Fetch 的记录文件留给 WP9b。

## 代码怎样工作

### 1. 不在块内切分

一段话只改了一个词，整段成对输出；代码组中只改了一种语言，整个代码组成对输出（6-2）。移到别处的块按“删去一处、加上一处”输出。

### 2. 整页只在一个通道中的页面

飞书表格的 `Release Channel` 为 `NEXT` 或 `RETIRE-IN-NEXT` 的页面，整页只在 UAT 或只在 Prod 显示。这种页面两个版本都校验，但只输出看得到的那个：`NEXT` 输出 `next`，`RETIRE-IN-NEXT` 输出 `current`，不输出成对标签。Fetch 的检查本来就不允许这两种页面中出现块级的 `<NextChannel>`。

### 3. 怎样证明合并是对的

合并结果按两种视图还原，必须分别等于两版各自的输出：

- **Prod 视图**：用 zdoc 网站生成 `.md` 副本与 `llms.txt` 时用的同一个函数 `resolveNextChannelCurrentView`（`apps/docs/plugins/next-channel-view.js`）。这同时证明了 `next` 独有的内容不会出现在静态产物中（6-4）；
- **UAT 视图**：反过来，去掉 `exclude` 中的内容。

比较时只放宽解析器确认的块之间的空行，块内的空白必须一字不差。除了逐条的用例，还用固定种子生成的随机块序列（插入、删除、重复、移动）检查两种视图都能还原。

### 4. 出错时

几种合并后可能显示错误内容的情况，一律失败，并指出原文中的位置：

| 情况 | 错误码 |
|---|---|
| Cloud 内容文件中手写的 `<NextChannel>` 落进工具生成的成对区域 | `MERGE_NESTED_CHANNEL` |
| 两版合并后出现重复的标题锚点（例如一个标题移了位置） | `ADAPT_UNSUPPORTED_MARKUP`，列出两处来源，提示用 `channel` 变换或改标题 |
| 成对区域中的代码块含有 `<NextChannel` 字样：Fetch 的检查会拒绝 | `ADAPT_UNSUPPORTED_MARKUP` |
| 没有闭合的代码块、只在一边的 Markdown 引用式链接定义、会让静态解析把生成的标签藏进代码块的长围栏 | `ADAPT_UNSUPPORTED_MARKUP` |

## 计划审阅的决定

在 [liyun95/zdoc#14](https://github.com/liyun95/zdoc/pull/14) 中审定，以 PR 中的[裁决评论](https://github.com/liyun95/zdoc/pull/14#issuecomment-6463394698)为准：

| # | 问题 | 决定 |
|---|---|---|
| R1 | 整页只在一个通道中的页面 | 两版都校验，只输出看得到的那个，不输出成对标签 |
| R2 | 相等的判据 | 正文严格比较，只放宽块之间的空行；front matter 与 `import` 分开断言 |
| R3 | 手写的通道标签、代码块中的通道指令 | 原样保留，对齐时不解释，两种视图对两边用同样的语义 |
| R4 | 重复的标题锚点 | 失败，不自动加后缀、不改链接 |
| R5 | 计划文件 | 同 WP10，标为 ready 前删掉 `.claude/plans/` |
| R6 | 代码块中的 `<NextChannel` 字样 | 在 PR 校验中失败，不改 Fetch 的检查 |
| R7 | 两版相同的路径 | 输出逐字节不变，md2md 的调用次数可以减少；“相同”指适配后的内容相同 |

## 一个例子：合成的 Delete Entities

测试 fixture `fixtures/merge/delete-entities/` 中，`current.md` 是 Delete Entities 的真实原文（milvus-docs [`3e6b749`](https://github.com/milvus-io/milvus-docs/commit/3e6b7499cbfcb6b5a365fb1f084a74836f625fc2)），`next.md` 是合成的：改写了开头一段、增加一个参数说明、改了一个 Python 示例。

<details>
<summary>合并后的开头一段</summary>

```mdx
<NextChannel action="exclude">

You can delete the entities that are no longer needed by filtering conditions or their primary keys.

</NextChannel>

<NextChannel action="include">

Synthetic next: remove obsolete entities using a filter or explicit primary keys.

</NextChannel>
```

还原成 Prod 视图后，是原来的开头一段与 Python 的 `ids=[18, 19]`；还原成 UAT 视图后，是合成的开头、新增的 `partition_name` 说明与 `ids=[118, 119]`。两种视图都与单独生成 `current`、`next` 的结果一致。

</details>

审阅时另做了一次真实页面上的验证：给第三批的 Stop（带两条 `remove`）造一个本地的 `next`，改写开头一段、改一行 Python 代码、新增一个三级标题，并在被删除的块里改一个标题。输出中只有 Stop 变了，有三处成对区域（那一段、整个代码组、新增的一节只有 `include`），被删除的块中的改动两边都不出现；两个手册的两种视图与单独生成的结果相比，只差连续空行的数量。
