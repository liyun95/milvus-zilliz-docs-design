# WP12 / WP13 共享接口约定（计划审阅版）

**状态（2026-11-02）**：最小固定输入、影响报告、锚点和采用单元接口已在 WP12-A 实现并通过[技术验收](./reviews/WP12-A.md)。B 的持久化与 GitHub 事务尚待审定；WP13 尚未启动。WP13 开工前还需统一技术设计 04/09 中等 SHA 的旧表述，并从合并后的公共接口建立执行计划。

| 约定 | WP12 上游更新 | WP13 提升 |
|---|---|---|
| 身份 | 用组 + 页面 ID 标识 Guides 更新单元；依赖页可组成同一个 PR | 输入组内页面集合，输出一次提升 PR |
| 基线 | 固定 master SHA、来源仓库/分支及 commit、旧 current/next、表格快照身份 | 固定 master SHA、待提升页面 current/next、通道变换和快照身份 |
| 变化报告 | 源及依赖变化、Cloud 输出变化、被覆盖的源变化、标题/锚点变化与引用位置、生成失败 | 消费或重新计算相同的锚点变化信息；不能只依赖 PR 正文或易失 artifact |
| 不变性 | Guides 只推进 next；生成候选无生产写入 | current 跟随 next；清理通道规则，保留手写 NextChannel，由报告提示人工处理 |
| 幂等 | 相同输入不提交重复变更；同页已有 PR 则更新；依赖页合并不能制造重叠 PR | 无有效变化不创建空 PR；明确报告不存在或无需提升的输入 |
| 并发 | 推送前核对远端 base/head；保护审核人修改；不 force-push | 同样核对远端；提升合并后 WP12 按新基线更新仍打开的 PR |
| 安全停止 | 网络/权限/快照不可用不等于页面已删除；无法认证页面状态时不关闭 PR | 无法确定目标、基线或锚点关系时不写生产状态，也不猜测替换 |
| 发布路径 | PR 合并后由现有定时/获准手动 Fetch 与部署采用 | 同左；不新增 master push 自动 Fetch |

后续接线必须保持的裁决与待办：

1. 变化报告哪些内容需要结构化保存，怎样从固定输入重算？公共类型放在哪里，谁维护？
2. 标题改名怎样建立可验证的锚点对应；多义、删除、跨页引用怎样处理？不得靠猜测批量改链接。
3. 已存在单页 PR 后才出现跨页依赖，如何合并处理、保留人工修改和审阅上下文？
4. 提升后滚动 PR 如何在不 force-push 的条件下更新；远端同时变化怎样安全重试或停下？
5. current/next 相同但存在 channel 变换时怎样判定可提升？产品需求已有该例子，不能只比较两个 SHA。
6. 候选构建、必要的 dev 快照与 GitHub PR 校验如何接线，特别是 GITHUB_TOKEN 创建 PR 后显式校验的权限与事件路径？
7. Rust 尚无 manual.yaml 实现：只预留按组/更新单元的边界，不现在落地或宣称完成手册级更新。待 R1 稳定后补整本手册 current/next 同步更新。

依据：[技术设计 04](../design/04-channels-and-lock.md)、[06](../design/06-upstream-changes.md)、[SDK Reference 草稿](../prd-sdk-reference.md)。若当前代码与设计不符，先提交具体冲突和建议，不在执行会话中自行改设计。

## A 已落实的裁决

- 报告区分 old-next→target 与 current→candidate-next；WP13 从固定输入重算，不依赖 PR 正文或易失 artifact。
- SHA 不同，或有待清理的 channel 变换时可提升；只有手写 NextChannel 不构成自动提升。
- 只对有证据的锚点对应作确定判断；多义和删除只报告，不自动改链接。
- 共享片段本身不强制合组；采用单元只纳入已证明的跨页依赖。
- B 的机器人提交 manifest、滚动 PR 事务与快照认证不属于 A 的已实现合同。远端状态不明时停止；不从 effective 快照推断删除。
