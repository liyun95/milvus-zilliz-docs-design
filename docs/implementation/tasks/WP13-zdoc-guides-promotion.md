# WP13 Guides 提升

**仓库**：[zdoc](https://github.com/zilliztech/zdoc)｜**阶段**：Phase 1b｜**依赖**：[WP11 双通道生成](https://github.com/zilliztech/zdoc/pull/921)｜**状态**：首片设计草案

## 目标

发版负责人选定本次上线的 Guides 页面。工具根据已验收的 UAT 版本生成提升候选，供负责人通过一条指向 `master` 的 PR 审阅和合并。目标是把验收过的内容带到生产：若 UAT 验收的是 `B`，该页从 `current=A / next=B` 提升为 `B / B`。

WP12 推进页面的 `next`，WP13 推进页面的 `current`。已有已验收的 UAT 版本就可以设计和验证提升，WP12 多页 Draft 与新 Fetch 的来源认证可以独立推进。现有 [#1334](https://github.com/zilliztech/zdoc/pull/1334) 的本地 `promote` 命令服务整本手册布局，Guides 首片应复用配置读取、通道生成及校验能力，保留整本手册的接口。

## 首片交付方式

1. **发版负责人显式选一页和一次 UAT 验收。** 首个样例选已激活、两端 SHA 不同且有可核验 UAT 记录的 Guides。先用本地命令生成候选补丁和报告，由人创建 PR。这样可以先验证内容是否正确，以及发版人实际如何提供验收凭据。
2. **把同一入口接入手动工作流。** 单页流程验证后，再让有仓库写权限的人手动发起，工具据同一候选开一条 Draft PR，人员审阅合并。跨页显式选择可以扩展到同次发版的一条 PR。工作流写权限、多页和 `all-pending` 各自需要验收。
3. **沿现有发布流程采用。** 提升 PR 合并后由正式 Fetch 生成至 dev，按已有站点 release/Jenkins 流程发版。提升工具的交付物是 PR 候选，部署由现有发布流程负责。

如果首版直接接机器人，仍需同一套 UAT 证据和视图比对，还要同时交付工作流权限和重跑防重复。先交本地候选能早点供发版人试用，后续工作流复用同一计划入口。

## 固定的输入与输出

| 输入 | 必须证明什么 |
|---|---|
| 页面 ID、待发目标、发版人确认 | 页面确实已激活。每个已配置目标都要纳入核对，如 Cloud、BYOC |
| UAT 发布记录与发版人验收 | 发布记录包含实际部署的 zdoc 提交、站点、构建或镜像身份。发版人确认本次页面和目标。构建成功本身不能代替内容验收 |
| UAT 部署提交中的生成记录及产物 | 从实际发布产物和记录交叉核对页面使用的 `next`、配置和生成输出。不能仅按现在的 dev tip 或工作流输入推断当时显示的内容 |
| 当前 PR 基线和页面输入 | 读取 `current/next`、共享配置、Cloud 内容和相关通道规则，校验候选基线。验收后 `next` 或影响视图的输入变化，报告差异并要求重新验收。基线前进时重建候选并重做检查 |

输出是一份候选补丁及一份可复核报告。报告列出旧 `current`、已验收 `next`、UAT 证据、受影响目标、允许的编辑和每项校验结果。证据缺失、无法恢复精确部署产物、存在未解释的配置差异或验证失败时，仅输出暂停原因。

## 补丁和审阅范围

- 首片仅提升明确选中的页面。`current` 采用已确认的 `next`，`next` 保留其原值。对同页明确可提升的 Transform，移除仅用于旧 current 的规则，解除要进入生产的 next 规则限定。保留手写 `<NextChannel>`，在报告中列出供人决定。
- 查找旧锚点的入链。首片若需改跨页 Git 链接、调整飞书整页通道，或无法确认锚点映射，暂停并列出必要动作。首个正例使用现有页面且无需这些配套变更。后续子片再实做经过认证的 Git 锚点修复、整页通道协调和仅本地规则变化的提升。
- 有同页开放更新 PR 时先暂停，提示合并、关闭或重新审阅该 PR。等后续补齐 WP12 重建接口，再处理提升后的自动重建。候选生成后，PR 检查重新核对同一验收输入和允许变更。
- 复用 WP11 的两通道生成。对每个配置目标，把候选的 Prod 视图与验收时的 UAT 视图比较，检查正文、代码、图片、标题锚点和页内链接。比较使用现有渲染语义，仅排除部署通道包装和环境标识差异，保留内容次序及链接目标。提升范围内由工具产生的双版本包装应消失。工具报告与人工发布动作各自留证。

## 验收与交接

| 验收 | 断言 |
|---|---|
| 正常单页 | 验收版本为 B 时生成 `A / B → B / B`。每个配置目标的候选 Prod 视图与已验收 UAT 视图一致，可按报告创建并复核一条 PR |
| 验收后变化 | `next` 从 B 到 C、配置或 Cloud 内容影响视图、UAT 证据来自错误构建，均暂停且无可用补丁 |
| 页面与链接边界 | 未激活、目标证据缺失、旧锚点需要协调、同页开放更新 PR、最终视图不一致，逐项报告阻塞 |
| 已提升或重复运行 | 无内容或规则变化时不生成空候选，原输入保持不变 |
| 正式发布旅程 | 本地候选和实际 UAT／Prod 分开记录。实际生产上线另需核对合并提交、Fetch 产物及部署记录 |

本卡只声明首片设计。需求 [8-1–8-4](../../prd.md#场景-8功能上线时提升) 保持待验收：首片验证本地候选与视图，工作流创建 PR、真实生产发布及既有更新 PR 自动重建分别结项。SDK 整本手册的完整提升旅程使用其独立契约。
